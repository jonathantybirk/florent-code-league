# eitri@557b395

Independent correction of Claude's modular atlas-planned mining opening. This
candidate is an economy benchmark, not a combat-flagship fork.

The earlier replay summary (`tools/evaluate_mining.py`) reported build cadence
but did not establish optimality. `tools/openbench.py` separates two questions:

- executor ratio: actual titanium versus the same plan with no wasted actions;
- planner ratio: that perfect plan versus the map's capacity-aware flow ceiling.

The baseline was not optimal: 91% executor ratio and 85% planner ratio over all
53 maps. Sweden was a correctness failure at 2,240 Ti, only 14% of its own
perfect schedule. Replay traces showed a finished Builder idling forever on a
tile needed by unfinished construction while the other crew repeatedly
replanned and sidestepped around it.

The fix is shared lifecycle state, not a terrain exception. The plan records
completed lane indices and permanent Harvester blockers. A finished Builder
moves one step off the network only when it currently occupies a tile belonging
to unfinished construction; it otherwise stays put, avoiding return traffic
through active lanes. Fallback BFS no longer routes through completed deposits.

Full-atlas do-nothing result at 1,000 rounds:

- total titanium: 1,502,210 versus 1,469,620 (+32,590);
- executor ratio: 93% versus 91%;
- eight maps improve and zero regress;
- Sweden: 15,200 versus 2,240 (94% versus 14% executor ratio);
- Icefloe +6,210, Royale +4,200, Longhouse +3,120, Fjordgate +2,410,
  Longship +1,970, Bifrost +1,080, String +640.

Rejected during diagnosis:

- delaying every zero-conveyor Harvester fixed Sweden but regressed six maps;
- sending every finished Builder home gained 50,590 Ti but lost 29,900;
- dropping all adjacent deposits reduced useful capacity;
- static construction occupancy still regressed String and Paths.

`tests/test_eitri.py` verifies complete lane assignment on every atlas map for
crew sizes 1 through 4. The focused suite is 15/15. The remaining 85% planner
ratio is explicitly not called optimal and is the next optimization target.

Online rounds use the current upper neighborhood led by Bean counters. Because
Eitri has no combat strategy, these games measure whether the opening survives
contact; it must not be auto-promoted over a combat flagship on economy alone.
